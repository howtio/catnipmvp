🎯 二、Runner 层原理（微调核心）

Runner 层是 catnip 中 最核心的层，负责将用户输入转化为工具调用计划并执行。微调直接作用于这一层的模型推理。

2.1 Runner 层内部结构

Runner 层由 4 个文件协同工作：

文件角色微调影响
provider.ts 定义 PlannedToolCall 接口、schema、normalizePlannedCalls 规范化、3 个 provider 工厂（Heuristic / AiSdk / DeepSeek） schema 定义了模型的输出格式（微调目标的输出空间）
local-provider.ts 🎯 微调直接作用文件 — Gemma 3 1B 模型的 generateObject 调用 + heuristic 规则覆盖 模型的 tool plan 在此生成，heuristic 在此覆盖
wrapper.ts createRunnerLayer — 编排执行流程：plan → executeToolCall 循环 → 结果 微调后仍然通过这里执行，无需改动
planner.ts summarizeToolOutcome、buildFinalAnswer 工具结果汇总 微调后保持不动

2.2 两种执行路径

路径 A: plan()
谁在用HeuristicProvider, LocalProvider, AiSdkProvider
流程模型一次性生成全部 tool plan → wrapper 逐工具执行
Gemma 3 1B✅ 当前路径（微调作用于此路径）
路径 B: runWithTools()
谁在用DeepSeekProvider
流程AI SDK 内置 tool calling 循环，模型自主决定调哪个工具
Gemma 3 1B❌ 1B 不支持（能力不够）
路径 C: Heuristic
谁在用HeuristicProvider（无模型时兜底）
流程纯关键词匹配，没有模型调用
Gemma 3 1B⚠️ 微调后退化时 fallback

2.3 Gemma 3 1B 模型在 Runner 中的完整工作流

1
构建 Prompt
将 system prompt、platform hint、tool list、working memory、用户输入拼接成完整 prompt
prompt = [SYSTEM, TOOL_LIST, WORKING_MEMORY, "Task: 用户输入"]
2
模型推理 — 这是微调发生的地方
generateObject({ model: gemma3:1b, schema: aiSdkPlanSchema, prompt }) — 模型根据 prompt 和 schema 约束输出结构化 JSON
输出: { plannedToolCalls: [{ name, args }], finalAnswerPrompt }
3
Heuristic 覆盖（local-provider 特有）
检查用户输入是否匹配关键词。匹配则丢弃模型输出，用 heuristic 规则替换。这是 1B 模型的兜底策略。
if (/写|创建|generate/.test(task)) → bypass model, use heuristic write_file
4
规范化 + 执行
normalizePlannedCalls 过滤未知工具、补全默认参数 → wrapper.ts 逐工具调用 executeToolCall
for (const call of plannedCalls) { await execToolCall(call) }

2.4 Heuristic 与模型的关系

// local-provider.ts: plan() 中的关键路径

const { object } = await generateObject({ model: llm, schema: aiSdkPlanSchema, prompt })
const plannedToolCalls = normalizePlannedCalls(object.plannedToolCalls, availableTools)

// ▼▼▼ Heuristic 覆盖：如果匹配关键词，丢弃模型输出 ▼▼▼
const writeTask = /写|创建|create|make|generate|code/.test(task)
const hasOpenIntent = /打开|预览|preview/i.test(task)

if (writeTask) {
  content = await generateContent(llm, task, ext)  // Route A: 模型生成真实内容
  heuristicCalls.push({ name: "write_file", args: { path, content } })
}
// ... 更多 heuristic 规则 ...

if (heuristicCalls.length > 0) {
  return { plannedToolCalls: heuristicCalls }  // ← 模型输出被完全覆盖
}

// ▼▼▼ heuristic 没命中 → 使用模型输出 ▼▼▼
if (modelProducedNoMeaningfulCalls(plannedToolCalls)) {
  return { plannedToolCalls: [] }  // 模型也没输出 → 直接回答
}
return { plannedToolCalls }  // 使用模型原始的 tool plan

2.5 Schema 定义（模型输出的 JSON 格式）

// provider.ts / local-provider.ts 中的 Zod schema
// 微调训练数据的输出格式与此完全一致

const aiSdkPlanSchema = z.object({
  plannedToolCalls: z.array(
    z.object({
      name: z.string(),                    // ← OpenAI 格式（原 toolName）
      args: z.record(z.string(), z.unknown()), // ← 参数 { path, content, query, ... }
    }),
  ),
  finalAnswerPrompt: z.string(),
})

🧠 三、微调原理

3.1 为什么要微调而非换模型？

❌ 当前 1B 模型的问题
  • 不知道何时调用工具（准确率 ~40%）
  • 依赖 heuristic 关键词匹配补救
  • heuristic 未覆盖的输入全部失败
  • 安全对齐过于保守（拒绝情书等合法请求）
✅ 为什么 LoRA 微调
  • 保留 1B 的推理速度（比大模型快 10x）
  • 仅需 ~$3 生成训练数据
  • Colab 免费 T4 可跑，45 分钟完成
  • heuristic 兜底：模型退化时不造成灾难
